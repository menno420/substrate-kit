## previous-session review

The previous card here is `2026-08-13-kit-release-v1.21.0.md`, "the seven-defect cut"
— the session that cut and published v1.21.0. Read rather than assumed, and it says
something sharper than "it left the registry alone": that session **consumed**
`docs/adopters.md`, running its A/B verification sweep *"against every tree in
`docs/adopters.md` at that hour's"* snapshot and describing "all 12 registry adopters".

So the registry was an **input to the release's own verification** while being stamped
**2026-07-21**, three weeks stale, and carrying at least one row (superbot-next at
v1.17.0, tree actually v1.20.2 since #602) that was wrong by four versions. Not
regenerating it before a release cut is the gap this refresh closes; its own card's
lesson — *"a fix reviewed only by its author is tested against exactly the cases its
author thought of"* — has an equivalent here: **a sweep is only as current as the
roster it sweeps.**

## Order

fleet-manager (#853), then superbot-next (#606) and superbot (#2436) adopted v1.21.0
today. The registry's rows still described the pre-wave fleet, and one of them
actively misled this session: it listed **superbot-next at v1.17.0** when its tree
had been at **v1.20.2** since #602. Regenerating it is the wave's aftermath.

## Result

`bootstrap currency` re-scanned all 12 roster repos and rewrote `docs/adopters.md`.
Corrected cells include superbot-next **v1.17.0 → v1.21.0 · current**, fleet-manager
**v1.20.1 → v1.21.0 · current**, superbot's tree **(none) → v1.21.0**, and
pokemon-mod-lab **unreadable → v1.15.0**.

**pokemon-mod-lab was not unreadable.** The first run recorded
`⚠️ unreadable — raw 404 on every probe; API contents HTTP 403; API repo probe HTTP
403; codeload tarball HTTP 403` for it. That is the *proxied* route's 403, not a
property of the repo: re-running with the GitHub hosts routed over direct egress read
it fine at **v1.15.0**. A row saying "unreadable" would have written a wall into the
fleet's most-read registry. Anyone running `currency` from a proxied environment
should set `NO_PROXY` for `api.github.com`, `raw.githubusercontent.com` and
`codeload.github.com` first.

## ⚠️ One row is knowingly wrong, and it is a finding, not a typo

`menno420/superbot`'s **config pin** cell reads `v1.0.0` and the row carries a
`⚠️ DRIFT` flag. **Both are false.** superbot's pin is `v1.21.0`, merged in sb #2436
(`6067b2d2`). Measured four ways at the time of writing:

| source | `kit_version` |
|---|---|
| `git show origin/main:substrate.config.json` | **1.21.0** |
| `api.github.com` contents (authenticated) | **1.21.0** |
| `raw.githubusercontent.com` **authenticated** | **1.21.0** |
| codeload branch tarball | **1.21.0** |
| `raw.githubusercontent.com` **unauthenticated** | **1.0.0** ← what `currency` reads |

The layered fetcher is documented as `raw → authenticated API → tarball`, and the raw
step is **unauthenticated for public repos**. Unauthenticated raw is served from a CDN
edge with its own cache key, and it returned the pre-merge value persistently — across
three regen attempts spanning ~15 minutes, and to a `Cache-Control: no-cache` request.
Because a stale copy is a valid **HTTP 200**, the fallback chain never engages: there
is nothing for it to fall through *from*.

**This is very likely why the registry lied about superbot-next in the first place.**
The stale `v1.17.0` row was not merely old — a raw-first read that cannot tell "current"
from "cached" reproduces exactly that failure, silently, on every regen.

Kept and shipped anyway, deliberately: the refresh corrects roughly eleven wrong cells
and introduces one, the wrong one is visibly flagged rather than silent, and the
alternative was leaving a three-week-stale registry in place. The correct fix is
upstream, not a hand-edit of a generated file.

## 💡 Session idea

**Authenticate the raw step, or drop it.** `currency`'s whole promise is "the tree is
truth"; an unauthenticated CDN read cannot keep that promise, because it returns a
confident 200 for a value that is no longer in the tree. Two candidate fixes for the
next kit session, both small: send the token on the raw request (my authenticated
probe of the same URL returned the correct value immediately), or reorder to
`API → tarball → raw` so the authoritative sources win and raw is only the
unauthenticated fallback it was meant to be. Either one is worth a regression test
that regenerates against a repo mutated seconds earlier — the exact condition under
which the current code is wrong and says nothing.
